# Release steps

Release steps, in this order (`X.Y.Z` the new version, `A.B.C` the previous one). A release is done only after step 9.
For now releases go out on GitHub only (APK, AppImage, Flatpak); stores (F-Droid, Flathub) come later.

1. Version `X.Y.Z` on a branch `release/X.Y.Z` in `app/CMakeLists.txt` (`project`, `QT_ANDROID_VERSION_NAME`, `QT_ANDROID_VERSION_CODE` = major·10000 + minor·100 + patch), `app/android/AndroidManifest.xml` (`versionName`, `versionCode`) and a `<release>` in `packaging/linux/io.github.shrippen.Mitori.metainfo.xml`.
2. Release log in `CHANGELOG.md`, before the tag: a section `## [X.Y.Z] — YYYY-MM-DD` below `## [Unreleased]` (newest first), with `### English` and `### Deutsch`, each a lead (what the release is about, one or two sentences), then the groups New, Improved, Fixed and Note (Neu, Verbessert, Behoben, Hinweis; breaking changes, steps the user must take) as `####`. Empty groups are left out. Each point says what changed for the user and why, not which code moved. The English part ends with `All changes: https://github.com/shrippen/mitori-app/compare/vA.B.C...vX.Y.Z` (the first release, without `A.B.C`: `…/commits/vX.Y.Z`). Check with `scripts/release-notes.sh --check` (CI runs it on every push) and read the notes with `scripts/release-notes.sh X.Y.Z`. The demo mode is never mentioned.
3. Landing page `docs/index.html` (Kante `.changelog`): the same text as a new entry at the top of `#changes`, both languages, compare link; from the fourth entry on, the oldest move into `details.changelog-more`. Bump the footer version. Graphics: a screenshot from the demo per visible change (`demo/shots.json`, `../shrippen.github.io/demo/tools/.venv/bin/python ../shrippen.github.io/demo/tools/screenshots.py mitori`, saved as `docs/shots/release-X.Y.Z-<name>-<lang>.webp`). Screenshots are taken only now, for a tagged release.
4. PR with steps 1–3, review as the skill `pr-review` says; the owner confirms the release in words (it publishes); CI green; merge on Gitea.
5. Tag the merge commit and push the tag to Gitea only (the mirror carries it to GitHub): `git tag -a vX.Y.Z -m "X.Y.Z" <merge commit> && git push origin vX.Y.Z`.
6. Gitea release, notes only, no files: `scripts/release-notes.sh X.Y.Z > notes.md && gt release create vX.Y.Z --repo shrippen/mitori-app --title "Mitori X.Y.Z" --notes-file notes.md --no-input`.
7. GitHub: the tag starts `.github/workflows/release.yml`, which creates the release with the same notes (it fails without the section) and attaches `Mitori-X.Y.Z.apk` (signed), `Mitori-X.Y.Z-x86_64.AppImage`, `Mitori-X.Y.Z-x86_64.flatpak` and `Mitori-X.Y.Z-aarch64.flatpak`, after checking that no demo code or data is in them. Check the run (`gh run list -R shrippen/mitori-app -w release.yml`) and that the release has all four files. A failed job: report it to the owner and stop; a fix goes through a PR first, and a new run that attaches files (`gh workflow run release.yml -R shrippen/mitori-app -f tag=vX.Y.Z`) only with the owner's permission in words, because it publishes on GitHub.
8. `python3 ../shrippen.github.io/overview/tools/build-versions.py`, then commit `docs/versions.json` in `shrippen.github.io` via a PR there.
9. Done when https://shrippen.github.io/mitori-app/ shows the release in `#changes` and the footer, and https://shrippen.github.io/versions.json has it.

`scripts/release-notes.sh` is a copy of Kante's `tools/release-notes.sh`: change it only there, then sync with `../Kante/tools/sync-release-notes.sh "$PWD"`.
